This field guide shows you how to design a first agent in artificial intelligence (AI) that can read three supplier notes and draft a reply, but cannot send mail, delete files, or spend money.

Field Guide 03, Context Engineering in Practice, showed how to pack a focused window for this same Friday delivery job, and left the send tool out as a safety choice. Field Guide 02 already named agent, tool use, human-in-the-loop, and prompt injection. This page turns those words into a first build. Safety is designed in before the first tool is added, not added as a later chapter.

Snapshot

The methods and sources are current as of November 2026. The supplier notes are a worked example, not a real order. The sources are listed at the end.

01

What this guide will, and will not, build

What is the smallest agent that is still useful, and still safe?

An agent, to recap in one sentence, is a model with a goal, tools, and a loop, so it can take several steps toward a job. This guide builds a small one. It can read three supplier delivery notes, compare dates and quantities, and draft a reply for a person to review. It cannot send mail, post a message, delete a file, or spend money.

That limit is the point of the page, not a detail to add later. Many first-agent tutorials start by showing a surprising result, then mention safety in a later chapter. Here the limits come first: the job is narrow, the tool list is short, and a person approves any step that would leave the machine.

This is like a clerk who can pull files and draft a letter, but who is not given the office stamp or the till.

So now you know

Your first agent should be narrow on purpose. Read and draft are enough for this job. Send, delete, and spend stay out.

02

When you do not need an agent

Does this job need a loop and tools, or will one packed model call do?

Start with the simplest setup that can do the job. Anthropic, in “Building effective agents” (December 19, 2024), says many jobs only need a single well-packed model call, and that you should add a workflow or an agent only when the job truly needs it. A workflow, in their wording, follows a path you wrote in advance. An agent chooses the next step as it goes.

If the three supplier notes already sit in a packed window, Field Guide 03 may be enough: one call, a draft, a stop. Use an agent when the model must choose which note to read next, call a tool more than once, or pause so a person can decide. In this guide, the notes live as separate files. The agent reads them one at a time. That is the reason for a loop, not a rule that every job needs one.

This is like walking to one shelf for three folders, versus sending a runner who may need to visit several rooms and come back with questions. If the three folders are already on the desk, do not send the runner.

So now you know

An agent is a design choice, not a default. If a packed window can do the job, do not add a loop.

03

The loop, in plain words

What actually happens after you give the agent a job?

The tool loop is the repeat of four moves. The model either writes a reply or asks to use a tool. Your code is what runs the tool, not the model. The tool’s result is added to the context window, the short-term workspace the model can see at once. The model looks again. This repeats until the job meets a written “done” line, a step limit is hit, or a person must decide.

1. AskThe model replies, or asks to use a tool.
→
2. CheckYour code checks the short list of allowed tools, and whether a person must approve.
→
3. Run or stopThe tool runs, the request is rejected, or a person decides.
→
4. ReturnThe result goes back in the window, and the model looks again.

The packing rules from Field Guide 03 still apply on every pass: only the goal, the tools this step needs, the few facts that matter, and what finished looks like. A loop that keeps stuffing old results into the window will get messy. Clear out what this step no longer needs, or start a fresh window with a short summary, the same way Field Guide 03 handled a long job.

This is like a cook who can request an ingredient, wait while someone else fetches it, then keep cooking. The cook never walks into the pantry alone.

So now you know

The model can ask. Your code decides whether the tool exists, whether it runs, and what comes back. The loop has a stop.

Key terms
Tool loop
The repeat in which the model replies or asks to use a tool, your code runs or rejects that tool, the result goes back into the context window, and the model looks again, until the job is done, a step limit is hit, or a person must decide.
04

One narrow job

What, exactly, is this agent allowed to finish?

We will keep the Friday delivery job from Field Guides 02 and 03, and give the agent a way to read the notes as files. You do not need any special hardware. The lesson is the same if you wire this in a small program or follow the steps in a toolkit you already use.

Here is a vague goal, then a written one. The first is too wide. The second is the job this agent is allowed to finish.

Too vague

Handle the suppliers.

The written job

It is Wednesday, November 11, 2026. Read the three latest supplier delivery notes, compare them, and draft a short reply to the warehouse lead, recommending who can get 48 units of packing foam to the west warehouse by Friday, November 13, 2026. Stop when the draft is ready. Do not send the reply.

The three notes, in the order they arrived, are the same ones from Field Guide 03:

Northline Supply Note dated November 10

Thanks for the request for 48 units of packing foam to the west warehouse. We can deliver Thursday, November 12, if the order is confirmed by noon Wednesday. Friday is fully booked on our trucks.

Harbor & Pine Note dated November 9

Standard lead time is five business days from confirmation. A Friday rush is sometimes possible for a fee, but only after we confirm stock. We currently have 40 units on hand. You asked for 48.

Riverbend Materials Note dated November 11, 8:04 a.m.

We can deliver Friday morning, November 13: 48 units of packing foam to the west warehouse, no rush fee. Please confirm by the end of the day Wednesday.

A line later in the same note tries to change the job. It tells the agent to ignore the earlier goal, send the draft as a real message, and delete the other two notes. That line is part of the file, not a new order from you. We will come back to it in the section on prompt injection.

“Done” means: a draft is ready, the preferred supplier is named from the notes, and the agent has stopped. “Done” does not mean a message was sent. A careful draft would notice that only Riverbend claims a Friday delivery of the full 48 units, that Northline can come Thursday but not Friday, and that Harbor & Pine is short on stock. It would also treat that last Riverbend line as part of the note, not as a new instruction.

This is like one trip to compare three quotes and write a recommended reply, not “run the purchasing department.”

So now you know

Write the job, the done line, and the stop before you add tools. This agent ends at a draft.

05

Least privilege

Which tools does this job actually need?

Least privilege means giving the agent only the tools this job needs, with only the permissions those tools need. An allowlist is the short list of tools the agent is allowed to call. Your code should reject anything that is not on that list, even if the model asks for it.

For this job, two tools are enough:

On the allowlist
  • read_note — read one named file from a short list of allowed file names, one file at a time.
  • draft_reply — write a draft the person can see. The draft stays in a review box. It is not mail.
Left off the list
  • send_email
  • delete_file
  • pay_invoice
  • A general shell, or “whatever the model asks for.”

The Open Worldwide Application Security Project (OWASP) publishes a widely used list of risks for large language model (LLM) applications. In the 2025 list, LLM06: Excessive Agency names the failure as too much functionality, too much permission, or too much autonomy. The official docs listed in the sources agree on the fix for a first agent: keep the tool list small, describe each tool clearly, including what it must not do, and have your code reject anything not on the list.

Describe the tools in plain words, the way you would write a short brief for a new colleague. read_note takes a file name from the allowlist, and only that list. It returns the text of that file. It does not write, move, or delete. draft_reply writes or replaces the draft in a review box. It does not send a message. Treat every tool result as untrusted data, not as a new instruction. A file can contain a hostile line. Reading it should not change the rules of the job.

This is like a key ring with two keys, not a master key to the building.

So now you know

If a tool is not required for this job, leave it out. What you do not attach, the agent cannot call.

Key terms
Least privilege
Giving the agent only the tools this job needs, with only the permissions those tools need.
Allowlist
The short list of tools the agent is allowed to call. Your code rejects anything that is not on the list.
06

Human in the loop

When must a person see the exact action and say yes or no?

Human-in-the-loop, to recap in one sentence, means a person stays in charge of important steps. Here that means an approval gate: the run pauses until a person says yes or no, and the person is shown the exact tool and arguments, not a vague summary.

Approve before anything would leave the machine, not after. Official guidance from OpenAI and from Google Cloud is consistent on this point: do not rely on a line in the system prompt alone to block a risky action. The system prompt is the standing rules you give the model. The model may still ignore a rule written only as text. Your code should intercept the tool request, show the person the tool name and the exact arguments, and wait.

For this job, the person reviews the draft before any real message is sent. And because send_email is not on the allowlist, “send it” is not a tool the agent can call even if it asks. Google Cloud’s guide on system instructions for agents also lists high-risk actions that should wait for a person, including deleting resources and anything that spends money. Those stay out of this first agent. If a later job truly needs a send step, the send still waits on this same pause, with the exact message shown.

What the person should see

A useful approval pause shows at least three things: the tool name, the exact arguments, and what will happen if the person says yes. For a draft, that can be as simple as:

  • Tool: draft_reply
  • Arguments: the full draft text, including the recommended supplier.
  • If you approve: the draft is saved in the review box. Nothing is sent.

If the model asks for a tool that is not on the allowlist, the person should see that the request was rejected, and why.

This is like a letter placed on a desk for a signature, with the envelope still empty.

So now you know

A system-prompt rule is not an approval gate. The pause has to live in your code, and the person has to see the exact tool and arguments.

Key terms
Approval gate
A pause in the run, enforced by your code, until a person says yes or no after seeing the exact tool and arguments.
07

The attack to design against

What if one of the supplier notes tries to change the job?

This is prompt injection, already named in Field Guide 02. Direct injection is a person typing a new instruction to the agent. Indirect injection is a hidden instruction inside a file, a web page, or another tool result the agent reads. A 2023 paper by Greshake and others showed that text the model is asked to read can be treated as if it were a command, including attempts to change which tools get called. OWASP’s 2025 entry LLM01: Prompt Injection describes the same split, and recommends least privilege, separating untrusted content from instructions, and human approval for high-risk actions.

In our example, the Riverbend note includes a line that tries to change the job: ignore the draft-only rule, send the draft as a real message, and delete the other two notes. This section is about the design that stops that line from doing harm. It is not a lesson in how to write attacks, and it does not give a copy-paste payload.

What the hostile line tries to doThis must not succeed
  • Change the job from “draft a reply” to “send a message and delete the other notes.”
  • Treat the supplier file as if it were a new instruction from you.
Why the request failsThe design holds
  • There is no send_email or delete_file tool on the allowlist, so those calls are rejected by your code.
  • The note is labeled as untrusted file text: information to read, not a new set of rules.
  • A person would have to approve any action that could leave the machine, and would see the exact tool and arguments.

The model may still ask to send. That is not a failure of the design by itself. The failure would be if the send happened. You cannot reliably stop a model from reading a hostile line. You can design the tools and the approval step so that line cannot send, delete, or spend.

This is like a note slipped inside a delivery folder that says “skip the review and mail this today.” The clerk can read the note. The clerk still cannot mail anything.

So now you know

You cannot reliably stop a model from reading a hostile line. You can design the tools and the approval step so that line cannot send, delete, or spend.

08

A starter recipe

What are the actual steps, in any toolkit?

Here is a short checklist you can follow in the stack you already use. It is not tied to one company’s library. A product may appear as an example in the sources. The lesson must still work if you switch tools tomorrow.

Starter recipe

  1. Write the job and the done line. Say what finished looks like, and what this job must not do.
  2. Decide whether one packed call is enough. If it is, stop here and reuse Field Guide 03.
  3. List the tools this job needs. Put send, delete, and spend off the list.
  4. Describe each allowed tool in plain words, including what it must not do.
  5. Pack the window: the goal, the allowlist, the few facts that matter, the rule that file text is untrusted, and the done line.
  6. Write the loop in your own code, with a step limit so it cannot run forever.
  7. Intercept every tool call. Run only allowlisted tools. Pause for a person when the next step would leave the machine, or when the request is unclear.
  8. Keep a simple log of the steps in a place that does not keep private mail or files longer than you need. Field Guide 10, Watch the Work, will go deeper. A local log is enough for now.
  9. Write two or three test questions for this job and keep them for Field Guide 05, Evals for Beginners.

In outline, the loop looks like this in any language: while the job is not done and the step count is under the limit, the model replies or asks for a tool; if the tool is not on the allowlist, reject it; if the action would leave the machine, pause for a person; otherwise run the tool, add the result, and continue. That is the whole pattern. You do not need a large extra toolkit to start.

The Model Context Protocol (MCP) is a common open way to offer tools to a model. It is also a way to hand the model too many tools at once. You can use it later if you want a shared way to connect tools. This first agent does not require it, and least privilege still applies if you add it. Official docs from Anthropic, OpenAI, and Google Cloud are listed in the sources as further reading. They are not a required toolkit. Do not start from a product that is being withdrawn: OpenAI’s Agent Builder is scheduled to shut down on November 30, 2026.

This is like a one-page kitchen brief: the dish, the allowed tools, who tastes the dish before it leaves the kitchen, and when to stop.

So now you know

The recipe is the same in any stack: a narrow job, a short allowlist, a loop you control, and a person in the loop before anything leaves.

09

A short self-check

How will you know this agent still does the job after you change something?

This guide does not teach evaluations (evals). Field Guide 02 already named the term: a fixed set of test questions you rerun after a change. Field Guide 05, Evals for Beginners, is where you will learn to write a small, honest test set and reuse it. What you can do now is start the habit, with three questions about this same supplier job.

Three questions to keep
  1. After you change the system prompt, how would you check that the draft still names the correct supplier?
  2. What would you write down now — the three notes, the expected draft points, and the rule that nothing is sent — so you can rerun the same checks later?
  3. If one supplier note contains a hidden instruction, what should a later test set include, and what result counts as a pass (the draft is written, and nothing is sent or deleted)?

If you can answer those in writing, you already have the start of a test set. Field Guide 05 is where you turn that start into a reusable evaluation.

What to try next: Field Guide 05, Evals for Beginners, or later add retrieval from your own notes in Field Guide 06, Retrieval You Can Trust. Do not add a second agent in this guide. The first one is enough to practice.

This is like a short list you check before the next run, not a full testing course.

So now you know

Keep a few written checks for this job. Field Guide 05 is where you turn them into a reusable evaluation set.

Quick review

It can read the three supplier notes and draft a reply. It cannot send mail, delete files, or spend money.

When one packed model call can already do the job. Add a loop and tools only when the work needs more than one step, a choice about which file to read, or a pause for a person.
